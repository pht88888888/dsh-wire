# dsh-wire

把电脑上的 DSH 会话接到手机上：手机直连电脑读真实会话，**不在本地复制一份对话**。

> 一个 npm 包，两端同装。电脑端负责把会话暴露出去（配 Cloudflare 快速隧道），
> 手机端负责把「远程会话」透明地接到本机的会话服务上。

---

## 为什么不用「本地镜像」

旧的远程方案是在手机上真的建一个会话、把电脑的事件抄进去。这条路必然脆弱：

- 抄写的一方要额外维护 `seq` 对齐与 turn 闭合；
- 只要有一行不符合引擎的 v4 格式，`dsh-session-format-v3-to-v4` 的读取侧**只重抛、不恢复**，
  整条会话就再也读不出来（表现为「会话从列表里消失」）；
- 于是每修一个 bug 就加一层补偿逻辑，bug 只会越修越多。

dsh-wire 换一条路：**手机端不持有会话数据。**

| | 镜像方案 | dsh-wire |
|---|---|---|
| 手机上的会话数据 | 自己维护一份副本 | **没有副本** |
| seq 对齐 | 必须校准 | 不存在 |
| turn 闭合 | 必须保证 | 不存在 |
| 写坏风险 | 会损坏会话列表 | 无盘可写 |
| 断线重连 | 要判断"我缺了哪几条" | 重新问电脑要即可 |

实现上就是一层薄代理：认得出远程 `sessionId`，把 `list` / `read` / `prompt` 转发给电脑；
其它 id 原样透传，**本地会话的行为一点不变**。

## 安装

```sh
# 电脑
npm i -g dsh-wire@<版本>

# 手机
npm i -g dsh-wire@<版本>
```

两端必须是**同一个版本**——协议版本不一致时会在 `hello` 阶段明确拒连，而不是"尽力兼容"。

## 配置

配置文件在 `~/.dsh/dsh-wire/config.json`（也可以写在插件的内联配置里，优先级更高）。

### 电脑端

```json
{
	"role": "desktop",
	"rendezvous": "https://wire.example.com",
	"cloudflared": "cloudflared"
}
```

- `rendezvous`：中转服务地址，用来让手机在隧道域名变化后找到你。
- `cloudflared`：可执行文件路径，留空则走 `PATH`。

启动后会：

1. 在 `127.0.0.1` 上起一个随机端口的 HTTP 服务；
2. 拉起 `cloudflared tunnel --url ...` 拿到 `https://xxx.trycloudflare.com`；
3. 把地址登记到中转，首次登记会生成 **6 位配对码**（5 分钟内有效，用后即焚）；
4. 隧道重启导致域名变化时自动续约，不需要人工干预。

配对码会打印到日志，也写在 `~/.dsh/dsh-wire/pairing.json`。

### 手机端

```json
{
	"role": "mobile",
	"rendezvous": "https://wire.example.com",
	"pairCode": "ABCDEF"
}
```

首次配对用 `pairCode`；配对成功后换发长期凭据，`pairCode` 可以删掉。
之后每次启动只做一次 `resolve` 拿当前地址，**域名怎么变都不用管**。

局域网调试可以跳过中转，直接写：

```json
{
	"role": "mobile",
	"desktopOrigin": "http://192.168.1.10:12345",
	"desktopToken": "<电脑端 ~/.dsh/dsh-wire/token.txt 的内容>"
}
```

## 部署中转服务

中转是**一台固定地址的小服务**，只保存 `设备 → 当前隧道地址` 的映射，
**不转发、不存储任何会话内容**。

```sh
node server/rendezvous.js --port 18907 --data /var/lib/dsh-wire
```

建议前面套一层 nginx / Caddy 提供 TLS。健康检查：`GET /health`。

端点：`/register`、`/resolve`、`/renew`、`/heartbeat`。
安全措施：配对码 5 分钟一次性、设备令牌只存 sha256 摘要、`/resolve` 每 IP 每分钟 20 次。

## 关于 Cloudflare 快速隧道的三个事实

官方文档（Quick Tunnels → Limitations）明确写了，本项目的设计直接照它来：

| 限制 | 本项目的处理 |
|---|---|
| **不支持 SSE** | 不用 SSE。事件走单通道长轮询，服务端最多挂 25 秒 |
| 单隧道 200 个并发请求 | 一台设备只开**一条**长轮询，in-flight 恒为 1 |
| 没有可用性保证 | 隧道崩溃自动重启（指数退避），地址变化自动续约 |
| 域名每次都变 | 由中转消除，手机端无感 |

## 验证

```sh
npm test
```

28 项，覆盖：

- **电脑端**：鉴权、路由、序列化、长轮询的"有数据立即返回 / 无数据挂起后唤醒"
- **手机端代理**：本地会话原样透传、远程会话转发、未经 `list` 直接按 id 打开也能命中、卸载后完整还原
- **端到端**：真实 HTTP 服务 + 真实客户端 + 真实代理，验证"手机看到电脑的会话、读到内容、把消息发过去"
- **中转**：配对码一次性、隧道地址变化后凭据解析到新地址、令牌校验、限速

## 已知限制

- 当前版本**只支持文本**。图片/附件会以事件形式原样下发，但手机端不回传附件。
- `ask` / 审批弹窗的转发已预留端点，尚未接入 `userQuestions` 的具体契约。
- 手机端不缓存会话内容：断网时远程会话不可读（这是"不复制"的代价，也是它不会写坏的原因）。
- 未接入 `rpc.intercept` 这层，而是包装服务方法——换来的是不依赖运行期端点命名。
